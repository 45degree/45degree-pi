# 第3章: 代码的坏味道

## 核心思想
代码的坏味道不是精确的衡量标准，而是一套启发式信号——它们"指出这里有一个可以用重构解决的问题"。培养识别坏味道的直觉，比死记任何量化指标都更重要。

## 引入的框架
- **坏味道（Bad Smells / Code Smells）**：Kent Beck 和 Martin Fowler 归纳的 24 种代码结构信号，每一种都指向可用的重构手法。
  - 何时使用：当你感觉代码"不太对劲"但说不出具体原因时，查阅坏味道列表寻找灵感。
  - 如何操作：识别出坏味道后，查阅"坏味道与重构手法速查表"，采用对应的重构手法消除。

## 关键概念
- **神秘命名（Mysterious Name）**：函数、模块、变量或类的名字不能清晰表明其功能和用法——改名是最常用的重构手法。如果想不出好名字，说明背后可能潜藏着更深的设计问题。
- **重复代码（Duplicated Code）**：同一代码结构出现在多处——合而为一后程序会更好。最单纯的形态是同一类的两个函数有相同表达式。
- **过长函数（Long Function）**：函数越长越难理解。关键不在于长度，而在于函数"做什么"和"如何做"之间的语义距离。每当感觉需要注释来说明，就应提炼为独立函数。
- **过长参数列表（Long Parameter List）**：参数过多令人迷惑——可用以查询取代参数、保持对象完整、引入参数对象、移除标记参数等方式缩短。
- **全局数据（Global Data）**：从代码库任意角落都可修改，无法探测哪段代码做了修改。首要防御手段是封装变量（132）。
- **可变数据（Mutable Data）**：对数据的修改常导致出乎意料的结果和难以发现的 bug。函数式编程的"不可变数据"理念值得借鉴。
- **发散式变化（Divergent Change）**：某个模块经常因不同原因在不同方向上变化——应将不同上下文拆分为独立模块。
- **霰弹式修改（Shotgun Surgery）**：每次变化需要在许多不同类内做许多小修改——应将相关逻辑集中到同一模块。
- **依恋情结（Feature Envy）**：一个函数跟另一个模块的数据交流远胜于自己所在模块——应搬移函数到它真正依赖的数据旁边。
- **数据泥团（Data Clumps）**：相同的三四项数据总是绑在一起出现（类字段、函数参数）——应为它们创建独立对象。
- **基本类型偏执（Primitive Obsession）**：用基本类型（整数、字符串）表示有业务含义的概念（钱、电话号码、坐标）——应以对象取代基本类型。
- **重复的 switch（Repeated Switches）**：同样的 switch 逻辑在不同地方反复出现——应以多态取代条件表达式。
- **循环语句（Loops）**：传统循环已显得过时——可以用管道操作（filter/map/reduce）取代。
- **冗赘的元素（Lazy Element）**：函数或类没有提供足够的价值——应内联或折叠。
- **夸夸其谈通用性（Speculative Generality）**：为"总有一天会需要"而添加的钩子和特殊情况——用不上的装置只会挡路。
- **临时字段（Temporary Field）**：类的某个字段仅为特定情况而设——应提炼到独立类中。
- **过长的消息链（Message Chains）**：一连串取值函数调用（a.b().c().d()）——应用隐藏委托关系。
- **中间人（Middle Man）**：类的接口有一半函数都委托给其他类——应用移除中间人，直接与真正负责的对象打交道。
- **内幕交易（Insider Trading）**：模块之间私下交换过多数据——应搬移函数和字段减少耦合。
- **过大的类（Large Class）**：单个类做了太多事——应提炼类、提炼超类或以子类取代类型码。
- **异曲同工的类（Alternative Classes with Different Interfaces）**：两个类功能相似但接口不一致——应用改变函数声明和搬移函数统一接口。
- **纯数据类（Data Class）**：只有字段和访问函数，没有行为——应将操作数据的行为搬移到类内。例外：拆分阶段得到的中转数据结构（不可变）。
- **被拒绝的遗赠（Refused Bequest）**：子类不想或不需要继承超类的函数和数据——如引起困惑可用以委托取代子类/超类；气味通常不浓，不必每次都处理。
- **注释（Comments）**：注释本身不是坏味道（反而是香味），但常被用作"除臭剂"掩盖糟糕的代码——当你感觉需要写注释时，先尝试重构让注释变得多余。

## 思维模型
- 当闻到坏味道时，不是直接开始重构，而是先查阅"坏味道与重构手法速查表"找到对应的重构手法——坏味道告诉你"该在什么时候做"，重构名录告诉你"该怎么做"。
- 将注释视为代码的"除臭剂"——如果你需要注释来解释一块代码做了什么，试试提炼函数（106）；如果提炼后仍需注释，试试改变函数声明（124）改名。
- 当面对重复的 switch 语句时，不是无条件消灭 switch，而是关注"重复"：多态的价值在于新增分支时只需加一个子类，而非在 n 处修改 switch。
- 当评估数据泥团时，使用"删掉一项测试"：删除众多数据中的一项，如果其他数据因此失去意义，就应创建新对象。

## 反模式
- **用注释掩盖烂代码**：代码有了长长的注释是因为代码本身很糟糕——应先重构消除坏味道，完成后注释往往变得多余。
- **无条件消灭所有 switch/if 语句**：多态是强大的工具，但并非所有条件逻辑都应消除。关键是不让同样的条件逻辑在多处重复。
- **过度封装导致"中间人"泛滥**：封装是好的，但一个类的一半接口都只是委托给其他类时，就是过度运用了——应移除中间人。
- **为测试而存在的函数/类**：如果函数或类的唯一用户是测试用例，这就飘出了"夸夸其谈通用性"的坏味道。
- **强迫所有子类继承所有东西**：子类不应该被强迫继承不需要的东西——如果引起困惑，用委托取代继承；但气味通常不浓，不必每次都处理。

## 代码示例
<!-- 坏味道识别示例：基本类型偏执 -->
<!-- Before: 用字符串和基本运算处理电话号码 -->
```cpp
#include <string>

// Primitive Obsession: telephone number as raw string
auto formatPhone(const std::string& phone) -> std::string {
    return "(" + phone.substr(0, 3) + ") " + phone.substr(3, 3) + "-" + phone.substr(6);
}
if (officeNumber.starts_with("800")) { /* toll-free logic */ }
```
<!-- After: 用 TelephoneNumber 对象封装行为 -->
```cpp
#include <string>

// Replace Primitive with Object (174)
class TelephoneNumber {
public:
    explicit TelephoneNumber(std::string raw) : _number(std::move(raw)) {}
    std::string areaCode() const { return _number.substr(0, 3); }
    std::string formatted() const {
        return "(" + areaCode() + ") " + _number.substr(3, 3) + "-" + _number.substr(6);
    }
    bool isTollFree() const { return _number.starts_with("800"); }
private:
    std::string _number;
};
```
- **演示了什么**：将字符串基本类型替换为领域对象，不仅消除了重复的格式化/判断逻辑，还使"电话号码"这一业务概念在代码中显式化。

## 工作示例（DEPTH=study 必须有）
### 从坏味道到重构手法的决策链

**场景**：代码审查时发现一个 `OrderProcessor` 类，每新增一种支付方式就需要修改其中的 3 个方法（计费、退款、对账），同时还要在另外 4 个类中修改日志和通知逻辑。

**第一步：识别坏味道**
- `OrderProcessor` 中 3 个方法因新增支付方式而同时修改 → **发散式变化（Divergent Change）**
- 日志和通知的修改散布在 4 个类中 → **霰弹式修改（Shotgun Surgery）**

**第二步：查阅速查表，匹配重构手法**
- 发散式变化 → 先用提炼函数（106）分开不同上下文的逻辑，再用提炼类（182）将支付相关的逻辑搬移到独立模块
- 霰弹式修改 → 用搬移函数（198）和搬移字段（207）把散布的日志/通知逻辑搬入同一模块；如数据相似，用函数组合成类（144）

**第三步：决定优先级**
- 先处理发散式变化（核心业务逻辑），因为它直接影响扩展性
- 再处理霰弹式修改（横切关注点），因为它增加了遗漏修改的风险

**重构后效果**：新增支付方式时，只需在支付策略模块中添加一个子类，日志/通知集中在单一模块中自动生效。

## 关键要点
1. 没有任何量度规矩比得上见识广博者的直觉——坏味道是指引方向的信号，不是必须遵循的铁律。
2. 神秘命名是最常见的坏味道——改名是最常用的重构手法；想不出好名字往往意味着更深的设计问题。
3. 函数的关键不在于长度，而在于"做什么"和"如何做"之间的语义距离——如果一段代码需要用注释说明，就应提炼为函数。
4. 全局数据的危险性与数量成指数关系——即便只有少量全局数据，也应封装起来。
5. 可变数据是 bug 的主要来源——应尽量分离有副作用的代码与无副作用的代码。
6. 注释是"香味"，但当注释是为了解释糟糕的代码时，它就是坏味道——尝试让所有注释都变得多余。
7. 如果你不知道该做什么，这才是注释的良好运用时机——记录"为什么做某某事"和不确定性区域。
