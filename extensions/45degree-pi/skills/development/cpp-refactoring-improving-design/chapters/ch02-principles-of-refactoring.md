# 第2章: 重构的原则

## 核心思想
重构是通过大量微小且保持软件行为的步骤，一步步达成大规模修改的特定清理方式——它不是与编程割裂的行为，而是日常编程中自然发生的、由经济利益驱动的实践。

## 引入的框架
- **两顶帽子（Two Hats）**：Kent Beck 提出的比喻——开发时在两个状态间切换。
  - 何时使用：每次编码前明确自己是"添加新功能"还是"重构"。
  - 如何操作：添加新功能时不修改既有代码，只添加测试和新代码；重构时不添加功能，只调整代码结构，不添加测试（除非处理接口变化）。
- **预备性重构（Preparatory Refactoring）**：在添加新功能前先重构，使新功能更容易添加。
  - 何时使用：发现对代码结构做微调能让后续工作容易得多时。
  - 如何操作：戴上重构帽子，先使用如函数参数化（310）等手法调整结构，再添加新功能。
- **三次法则（Rule of Three）**：事不过三，三则重构。
  - 何时使用：第一次做某事只管做；第二次做类似事产生反感但还做；第三次再做就必须重构。
- **捡垃圾式重构（Litter-Pickup Refactoring）**：顺手清理遇到的"垃圾"代码。
  - 何时使用：已理解代码但发现它做得不好，且重构成本很低时；若需较多精力，记下来稍后处理。
- **营地法则（Camping Rule）**：离开时让营地比来时更干净。
  - 何时使用：每次触碰代码时都让它变好一点点。
- **Branch By Abstraction**：用于长期重构的策略——引入抽象层同时兼容新旧接口，逐步迁移调用方后再替换底层实现。

## 关键概念
- **重构（名词）**：对软件内部结构的一种调整，目的是在不改变软件可观察行为的前提下，提高其可理解性，降低其修改成本。
- **重构（动词）**：使用一系列重构手法，在不改变软件可观察行为的前提下，调整其结构。
- **结构调整（Restructuring）**：对代码库进行的各种形式的重新组织或清理——重构是特定的一类结构调整。
- **设计耐久性假说（Design Stamina Hypothesis）**：通过投入精力改善内部设计，可以增加软件的耐久性，从而更长时间地保持开发的快速。
- **YAGNI（You Aren't Going to Need It）**：不预先添加用不到的灵活性机制——只有当未来重构会很困难时，才考虑现在添加灵活性。
- **已发布接口（Published Interface）**：接口的使用者与声明者彼此独立，声明者无权修改使用者的代码——这会限制重构。
- **持续集成（Continuous Integration / Trunk-Based Development）**：每个团队成员每天至少向主线集成一次，避免分支差异过大导致合并困难。
- **演进式架构（Evolutionary Architecture）**：先基于当前需求构造软件，随着理解加深通过重构调整架构。

## 思维模型
- 当不确定该添加功能还是该重构时，自问"现在戴的是哪顶帽子"——两顶帽子的切换可以在10分钟内发生多次，但必须清楚当前状态。
- 将重构视为经济利益驱动的行为，而非道德洁癖——"我们之所以重构，因为它能让我们更快：添加功能更快，修复bug更快。"
- 当评估是否要为未来变化添加灵活性时，使用"未来重构难度"作为判断标准：如果以后重构不会太难，现在就不加。
- 将测试视为bug检测器——"把我想要达成的目标写两遍，代码写一遍，测试写一遍，我就得犯两遍同样的错误才能骗过检测器。"

## 反模式
- **将重构与功能添加混合提交**：试图在版本控制中严格分离两者，这往往不值得——重构常与新功能紧密交织，分离会使其脱离上下文。
- **专门安排"重构冲刺"或"重构迭代"**：重构不应是计划中的专项活动，而应融入日常编程流；大规模的专门重构应很少发生。
- **在缺乏测试的遗留系统上大规模重构**：没有测试覆盖时，应用接缝技术逐步插入测试，而非一鼓作气重写。
- **为实现高性能而持续牺牲代码清晰度**：持续关注性能通常收效甚微；应先用度量工具找到性能热点，仅优化热点代码。
- **细粒度强代码所有制**：给每段代码指定唯一所有者会带来接口维护的麻烦——推荐团队代码所有制或开源模式。

## 工作示例（DEPTH=study 必须有）
### 克莱斯勒综合薪资系统性能优化纪实

Ron Jeffries、Kent Beck 和 Martin Fowler 面对一个支付过程太慢的薪资系统。

**臆测阶段**：团队基于对系统的全盘了解，推测了几种可能的性能瓶颈，讨论了几种优化方案，自认为找到了真正的好点子。

**度量阶段**：用 Kent 的性能度量工具实测后发现——他们臆测的所有可能性全都不是问题肇因。真相是：系统把一半时间用来创建"日期"实例，且这些实例都有相同的几个值。

**优化阶段**（约 5 分钟）：
1. 发现日期对象在创建时经过了不必要的字符串转换过程
2. 发现很多日期对象都被用来产生"日期区间"，而绝大多数日期区间是空的
3. 重构：提炼出工厂函数专门创建"空的日期区间"
4. 优化：让工厂函数始终返回同一个不可变的"空日期区间"对象，而非每次新建

**结果**：系统速度几乎提升一倍，测试速度达到可接受程度。

**教训**：哪怕你完全了解系统，也请实际度量它的性能，不要臆测。臆测会让你学到一些东西，但十有八九你是错的。

## 关键要点
1. 重构的关键在于运用大量微小且保持软件行为的步骤——代码很少进入不可工作状态，可在任何时刻停下来。
2. 重构的唯一目的就是让开发更快，用更少的工作量创造更大的价值——始终由经济利益驱动。
3. 不必告诉不懂技术的经理你在重构——软件开发者是专业人士，最快的方式就是重构，所以你就重构。
4. 性能调优的正确流程：先用度量工具找热点 → 集中优化热点代码 → 小步修改、编译、测试、再度量 → 未提升就撤销。
5. 自测试代码、持续集成、重构这三大实践彼此之间存在很强的协同效应——三者是 YAGNI 和敏捷开发的基础。
6. 数据库重构的关键：借助数据迁移脚本，将数据库结构的修改与代码相结合；可采用并行修改（expand-contract）策略分多次生产发布完成。
7. 特性分支存在时间越长，合并难度指数上升——持续集成（CI）与重构能良好配合，特性分支对重构的阻碍太严重。
