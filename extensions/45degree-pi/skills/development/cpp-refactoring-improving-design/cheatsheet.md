# 重构速查决策表

> 按"当X→做Y，因为Z"格式。**决策工具，非术语表**。

## 1. 核心决策框架

**两顶帽子**（每次编码前必问）：
- 添加功能 → 不加原有代码，只加测试+新代码
- 重构 → 不加功能，只调结构。10分钟内可切换多次

**何时重构（决策树）**：
```
代码需修改？
├─ 结构方便加特性？→ 否 → 先重构再加特性（预备性重构）
└─ 第几次做类似修改？→ 第3次 → 必须重构（三次法则）
代码不需修改？→ 不重构
```

**重构vs性能**：先重构后优化。结构良好→易找热点→易优化。先度量，别臆测。

## 2. 阈值速查

| 信号 | 阈值 | 动作 |
|------|------|------|
| 参数个数 | >3 | 以查询取代参数 / 引入参数对象 |
| 同一类型分支重复函数 | ≥2 | 以多态取代条件表达式 |
| 数据项成群出现 | ≥3项 | 提炼类（数据泥团）|
| 类接口委托占比 | >50% | 移除中间人 |
| 子类差异 | 仅1个字段值 | 移除子类，用字段替代 |
| 变量赋值次数 | >1（非循环/收集）| 拆分为多个const变量 |

## 3. 坏味道→重构手法

| 坏味道 | 首选手法 |
|--------|----------|
| 神秘命名 | 改变函数声明 |
| 重复代码 | 提炼函数 |
| 过长函数 | 提炼函数（用注释当函数名） |
| 过长参数列表 | 引入参数对象 / 以查询取代参数 |
| 全局数据 | 封装变量 |
| 可变数据 | 封装变量 / 以查询取代派生变量 |
| 发散式变化 | 提炼函数→提炼类 |
| 霰弹式修改 | 搬移函数+搬移字段 |
| 依恋情结 | 搬移函数到它依赖的数据旁边 |
| 数据泥团 | 提炼类 |
| 基本类型偏执 | 以对象取代基本类型 |
| 重复switch | 以多态取代条件表达式 |
| 循环语句 | 以管道取代循环(map/filter) |
| 冗赘元素 | 内联函数/类 |
| 夸夸其谈通用性 | 内联函数/移除死代码 |
| 临时字段 | 提炼类 |
| 过长的消息链 | 隐藏委托关系 |
| 中间人 | 移除中间人 |
| 内幕交易 | 搬移函数+搬移字段 |
| 过大的类 | 提炼类 |
| 异曲同工的类 | 改变函数声明统一接口 |
| 纯数据类 | 搬移函数（将行为搬入） |
| 被拒绝的遗赠 | 以委托取代子类/超类 |
| 注释(除臭剂) | 提炼函数让注释变得多余 |

## 4. 继承vs委托决策矩阵

| 维度 | 继承 | 委托 |
|------|------|------|
| 关系 | is-a（是什么） | has-a（有什么） |
| 变化维度 | 仅1个 | 可多个 |
| 耦合 | 紧耦合 | 松散 |
| 信号 | 多函数有相同类型分支 | 需要第2个变化维度 |

> 继承是"只能打一次的牌"。先用继承表达主维度，遇第二维度→以委托取代子类。

## 5. API设计速判

- 有返回值+有副作用？→ 分离查询与修改（CQS）
- 参数是布尔字面量？→ 拆为两个具名函数
- 调用者拆散对象传参？→ 保持对象完整传整个对象
- 参数可被函数自身获取？→ 以查询取代参数
- 依赖全局对象难测试？→ 以参数取代查询
- 字段创建后不应变？→ 移除设值函数

## 6. 安全重构节奏

① 确保有可自检的测试 → ② 婴儿学步（每次最小修改）→ ③ 每步后运行测试 → ④ 失败→回滚，步子拆更小重做 → ⑤ 通过→提交 → **"红条时永远不许重构"**
